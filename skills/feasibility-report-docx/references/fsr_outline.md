# 可研报告五章写作指引

通用的信息化项目可行性研究报告结构。不同模板章节名可能微调，但骨架一致。写作时先读模板的实际标题，再按下面的对应关系落笔——**不要用本文件的标题去覆盖模板标题**。

---

## 第一章 项目概述

### 1.1 项目名称

用立项批复口径的完整名称。模板里通常有 `【项目名称】` 之类的占位，注意全文一致，不得一处简称一处全称混用。

### 1.2 项目建设单位

`{建设单位全称}`，首次出现时写全称并括注简称，后文统一用简称。

### 1.3 编制依据

**这一节基本照抄模板，不要改写。** 通常包含：

- 国家/行业主管部门关于本领域的规划、意见、管理办法；
- 相关的国家标准、行业标准（GB/T、GB 5xxxx 等）；
- 建设单位上级集团的采购/信息化管理制度；
- 本项目已批复的立项文件、预算文件。

只保留**与本项目业务真正相关**的条目。模板里显然属于原项目业务、与本项目无关的依据要删掉；本项目确实引用的法规要补进去。伪引用（写了文号但内容对不上）比不写更糟，宁缺勿错。

### 1.4 项目建设背景

四段式，缺一段就会显得空：

1. **单位定位与现状** —— 建设单位是什么性质的单位、业务规模、现有信息化基础。从参考文档取口径，不要编数字。
2. **外部要求** —— 政策、监管、上级集团要求带来的压力。政策名称与文号必须真实可核。
3. **内部痛点** —— 现有业务方式的 4～6 个具体问题，每条落到"哪个环节、慢在哪、错在哪、风险在哪"，不要写"效率有待提升"这种无信息量的话。
4. **建设契机** —— 技术条件已成熟、试点已验证、上级已明确要求，一句话收到本项目上。

痛点必须与第三章的建设内容一一咬合：背景里提的问题，方案里必须有模块对应解决。提了问题不解决，评审核查时是硬伤。

### 1.5 项目建设目标

分条写，每条一个可验证的结果，不写过程。

弱写法：「提升采购效率，降低管理成本。」
强写法：「实现采购文件智能编制，编制环节耗时由 X 人天压缩至 Y 小时，效率提升 80% 以上。」

目标数量控制在 5～8 条，且必须能映射到建设内容模块。技术指标（准确率、覆盖率、响应时间、并发数）要与建设内容或需求书里的承诺一致，**不要在此处拔高**——承诺了就是验收依据。

## 第二章 总体建设方案

### 2.1 建设原则

模板通常给 4～6 条固定原则名（先进性、可用性、安全性、可维护性、可扩展性、经济性等）。原则名照抄，**每条正文重写**，且必须落到本项目的具体做法上。

判断标准：把单位名换掉，这段话如果对任何项目都成立，那就是废话，要重写。

- 差：「系统采用先进技术，保证技术领先。」
- 好：「采用 {技术路线}，实现 {具体能力}，较现有人工方式在 {某指标} 上提升 {幅度}。」

### 2.2 总体架构

分层描述最稳妥，通常四层：基础设施层 / 引擎（或能力）层 / 应用层 / 访问交互层。

- **基础设施层**：明确是利旧还是新建。利旧要写清依托现有资源，这是投资合理性的关键。
- **引擎层**：列出本项目的核心能力组件，说明部署方式（私有化/云），以及与数据安全的关联。
- **应用层**：按建设内容模块逐一点名，顺序与建设内容清单一致。
- **访问层**：说明访问方式（Web/移动/接口）与对接的外部系统。

如果模板此处有架构图，**保留原图占位**，在文字里说明层级；不要在工具里尝试替换图片。

### 2.3 系统建设内容（篇幅主体）

按建设内容清单逐模块展开，**一个模块一个三级标题**，顺序、名称与清单严格一致。

每个模块的小节写法统一为四段：

1. **建设目的** —— 解决第一章背景里的哪个痛点；
2. **功能构成** —— 3～6 条主要功能，动词开头；
3. **实现方式** —— 用什么技术/流程实现，与哪些模块或外部系统交互；
4. **交付效果** —— 可验证的结果或指标。

金额或工作量在清单里有时，**不要写进正文**（金额属于商务内容），但要在心里核对：大金额模块的篇幅应当更长，篇幅与投入明显不匹配会显得报价虚高。

### 2.4 系统集成与定制开发

逐个对接系统写：**对接对象 → 对接内容（数据/单点登录/流程）→ 对接方式（接口/中间库/文件）→ 责任边界**。用表格比段落清晰。

必须明确"哪一方提供接口"这类边界，否则实施阶段必然扯皮，评审也会问。

### 2.5 硬件设备

若本项目不含硬件，本节改写为"依托现有基础设施，本项目建设不涉及新增硬件投入"，并说明现有资源的可用性判断依据。**不要保留模板的硬件清单**。

## 第三章 项目实施周期

一张进度表 + 一段说明。表格列通常是：序号 / 起止时间 / 主要内容 / 交付物。

要点：

- 阶段划分按"立项 → 委托 → 需求与设计 → 开发部署 → 集成联调 → 测试 → 初验 → 终验"，8 个阶段左右；
- 每个阶段的**交付物必须是具体文档名**（实施方案、需求规格说明书、测试报告、验收报告），不写"完成相关工作"；
- 需求阶段要把**需要人工前置准备的成果物**列进去（如范本梳理、规则梳理、数据治理），这类工作往往是工期风险点，写进表格等于提前免责；
- 时间跨度与合同工期一致，与用户口头承诺的时间不能打架。

## 第四章 经济与社会效益

分经济效益与社会效益两块，**效益要与投资额形成可推演的关系**，不要只写形容词。

经济效益的常见可推演口径：

- 人力节约：`涉及岗位人数 × 单次耗时 × 年发生次数 × 节约比例 = 年节约人天`，再折算金额；
- 成本避免：废标/流标/重复采购导致的损失，按历史发生率估算；
- 合规收益：审计、巡察问题的整改成本下降。

社会效益落到：管理透明度、监管能力、示范效应、对上级集团战略的支撑。**避免写成宣传稿**，每条都要能对应到方案里的某个能力。

数字口径务必自洽：人天节约数与前面章节的效率提升承诺要对得上，不能一处说提升 80%、另一处算出节约 50%。

## 第五章 主要结论与建议

### 5.1 可行性结论

四维结论，每个维度 1～2 段：

- **业务可行性**：需求真实、流程清晰、有制度依据；
- **技术可行性**：技术路线成熟、有同类案例、集成风险可控；
- **经济可行性**：投入产出比合理、投资规模与效益匹配；
- **安全可行性**：部署方式、数据边界、权限与审计满足要求。

### 5.2 建议

4～6 条，聚焦"项目成立后必须做对的事"，不写空话。有价值的方向：

- 组织保障（谁牵头、谁配合、决策机制）；
- 制度配套（范本、规则的固化与更新机制）；
- 数据准备（历史数据治理、供应商主数据）；
- 分期推进（先核心后外围，控制一次性风险）；
- 培训与推广（分角色培训、试点先行）；
- 运维与调优（模型/规则持续迭代的责任主体）。

**不要写"建议尽快立项""建议加强领导"这类无落点的句子。**

## 建设内容 → 章节的映射方法

拿到建设内容清单（尤其是报价单）后，先做一张映射表，再动笔：

| 清单条目 | 金额/权重 | 对应章节 | 小节标题 | 篇幅权重 |
|---|---|---|---|---|
| 模块 A | | 2.3 | | 高 |
| 模块 B | | 2.3 | | 中 |
| 平台/门户 | | 2.3 | | 中 |
| 能力引擎 | | 2.2 + 2.3 | | 高 |
| 集成开发 | | 2.4 | | 中 |

映射表做完，篇幅分配和遗漏检查就同时有了依据。清单里每一条都必须在这张表里有落点，一个都不能少。
